# Tashinami — コンセプトドキュメント

> 飲んだお酒を、静かに、愛おしく記録する。

飲んだお酒を記録するための Web アプリ。日々の一杯を丁寧に残し、
振り返り・発見・年に一度の物語（サマリー）へとつなげる。

---

## 1. コンセプト

**「嗜（たしな）み」** — たしなむこと。ほどよく、品よく、味わうこと。

Tashinami は「たくさん飲んだ量」を競うアプリではない。
**一杯ずつと向き合い、その記憶を静かに積み重ねる**ための場所。
記録が溜まるほど、自分の好み・行きつけ・季節の移ろいが立ち上がってくる。

### プロダクトが大切にする 3 つのこと

1. **記録が負担にならない** — 飲んだ直後でも、数タップで残せる。
2. **振り返りが楽しい** — TOP10・マップ・年次サマリーで「自分の物語」が見える。
3. **佇まいが良い** — 大人が使って気恥ずかしくない、落ち着いた美しさ。

---

## 2. トーン & マナー（デザイン方針）

**基調は「大人で落ち着いた雰囲気」。要所に遊び心。**

| 観点 | 方針 |
| --- | --- |
| 全体の空気 | 静謐・上質・余白多め。バーの間接照明のような落ち着き。 |
| 配色 | 低彩度のダークトーンを基調（深い墨・琥珀・葡萄・翠など、酒を想起する色を差し色に）。 |
| タイポ | 可読性の高い明朝／セリフをアクセントに、本文はサンセリフで整える。 |
| モーション | 控えめでなめらか。記録完了・サマリー公開など「ハレの瞬間」だけ気持ちよく動かす。 |
| 遊び心の置き所 | 記録完了時のひとこと、TOP10 の演出、年次サマリーの物語的な見せ方、空状態（empty state）のコピー。 |

> **遊び心の原則**：常時ふざけない。要所（達成・振り返り・空状態）にだけ効かせることで、
> 落ち着いた土台とのコントラストで効く。

---

## 3. 想定ユーザー / 利用シーン

- **誰が**：お酒（種類問わず）を嗜む大人。記録・振り返りが好きな人。
- **いつ**：飲みながら／飲んだ直後（モバイル）、後日ゆっくり振り返り（PC）。
- **デバイス**：**モバイルと PC を同等に重視**。**デバイスで機能差はつけない** —
  すべての機能を、単一のレスポンシブデザインで両デバイスに提供する。
  - モバイル／PC で「できること」は完全に同じ。出し分けや機能制限はしない。
  - 画面幅に応じてレイアウト・情報密度・操作導線を最適化する（機能ではなく見せ方で最適化）。
    - モバイル幅＝片手・数タップで素早く記録できる導線。
    - PC 幅＝一覧・マップ・サマリーを俯瞰して振り返りやすいレイアウト。

---

## 4. スコープ

### 対象のお酒：**お酒全般**

ビール・ワイン・ウイスキー・日本酒・焼酎・カクテル等を **カテゴリで分類**して記録。
カテゴリごとに任意のメタ項目（例：ワインなら産地・品種、日本酒なら蔵・精米歩合）を
持てる設計を目指す（段階的に拡張）。

### 共有の性質：**個人記録 ＋ 限定共有**

- 基本は自分のためのプライベートな記録。
- 特定の記録や年次サマリーを **リンク等で限定的に共有**できる（フル SNS 化はしない）。

## 5. 機能ロードマップ

「作りたい」と合意した範囲。順番はマイルストーンの目安。

### Phase 1 — 記録（コア）

- お酒の記録 CRUD（銘柄／カテゴリ／評価／メモ／日時／写真など）。
- カテゴリ分類とタグ。
- 一覧・検索・絞り込み（TanStack Table を活用）。

### Phase 2 — 出会った場所

- その一杯と **どこで出会ったか** を記録する（買った酒屋・飲んだ店・旅先の蔵・贈り物・通販）。
- **「飲んだ場所」は取らない。** 家飲み中心の人には自宅にピンが 1 本立つだけで、
  位置入力という記録中でいちばん重いコストに、振り返りが見合わない。
- 出会いの場所は図鑑（何と初めて出会ったか）と同じ軸。溜まると **酒屋ごとの棚** が立ち上がり、
  「この店のセレクトは自分に合う」が見えてくる。外飲みの人にとっての「行きつけ」に対応するものが、
  家飲みの人にとっては酒屋になる。
- **テキストで溜める**（銘柄と同じサジェストで補完し、表記揺れで棚が割れないようにする）。
- **常設のマップページは作らない。** 場所の価値は「酒屋ごとの棚」でほぼ回収できる。
  地図が上乗せするのは *旅先の可視化* だけで、それは年に数回の出来事。毎日開くページにすると、
  ほとんどの日は同じ 2〜3 本のピンを眺めることになる。地図は Phase 4 の 1 カットとして咲かせる。
- 通販・贈り物は座標を持たないが、出会いの場所としては一級で扱う（地図に載らないだけ）。
- 自宅飲みそのものの振り返りは、場所ではなく **時間軸**（曜日・時間帯・季節）が担う。

### Phase 3 — TOP10（殿堂）

**順位は評価から計算しない。本人が選んで、本人が並べる。**

- 絶対評価で順位は作れない。好きな酒はどれも 9〜10 に貼りつく（天井効果）ので、
  10 点が 20 個並んだとき、順位を決めているのは **タイブレークのルール**であって本人の好みではない。
- だから TOP10 は計算結果ではなく **意思**として持つ（`top_drinks`：ユーザーごと 1 行、
  配列順がそのまま順位）。席は 10 で固定する。**有限であることがこの機能の価値**で、
  11 個目を入れたければ何かを降ろすことになる。その選択こそが「自分の好み」の表明になる。
- 評価は **候補の推薦順**としてだけ効く。入口を提案するのが評価、席を決めるのは本人。

#### 評価と順位は、測る対象が違う

混同すると必ず破綻するので、ここを正本とする。

| | 何を測るか | 誰が決めるか |
| --- | --- | --- |
| **評価（0〜10 のスライダー）**<br>UI では「**この一杯の印象**」と呼ぶ | **その夜の一杯**。グラス 1 杯、その日の体調、その場の空気まで含めた印象。 | 記録するとき、その場で |
| **殿堂（TOP10）** | **銘柄**。生涯の中でのその酒の席。 | 落ち着いてから、本人が選ぶ |

対象が違うのだから、**10 点が 20 個あっても矛盾しない**（良い夜が 20 回あっただけ）。
UI では、記録フォームの評価欄と TOP10 の候補欄の 2 箇所でこの区別を明示する
（誤解が生まれるのは「点を付けている瞬間」なので、そこに書く）。

### Phase 4 — 年次サマリー（Spotify Wrapped 的）

- 1 年分の記録を **物語仕立てのサマリー**に。
- 例：総杯数、最も飲んだカテゴリ／銘柄、新しく出会った数、よく出会った場所、
  季節ごとの傾向、TOP10、印象的な一杯。
- **出会いの地図はここで出す。** 「今年、あなたはここで酒と出会った」——
  一年分のピンが一度に灯るカット。旅先の一杯がいちばん映えるのはこの文脈で、
  年 1 回しか出さないから地図プロバイダのコストも作り込みも正当化できる（→ §8）。
- **限定共有**できるビジュアルなカードとして仕上げる。

### 将来拡張（今回のスコープ外）

## 6. 画面構成（想定）

- **記録**：一覧／新規作成／詳細・編集。モバイルでは素早い入力導線。
- **図鑑**：初めて出会った一杯のコレクション。出会った場所もここに紐づく。
- **TOP10**：ランキングビュー。
- **サマリー**：年次の物語ページ（共有用ビジュアル込み）。
- **認証**：ログイン／サインアップ（Supabase Auth・実装済み）。

---

## 7. 技術スタック（このテンプレート準拠）

- **フレームワーク**：TanStack Start（React 19）＋ ファイルルーティング（TanStack Router）。
- **データ**：Supabase（`@supabase/ssr`）／serverFn ＋ TanStack Query（楽観更新）。
- **バリデーション**：zod（スキーマは `src/schemas/`）、`neverthrow` によるエラーハンドリング。
- **UI**：Tailwind CSS v4 ＋ Radix UI ＋ `lucide-react`。
- **フォーム/テーブル/状態**：TanStack Form / Table / Store。
- **デプロイ**：Cloudflare（`@cloudflare/vite-plugin`）。

> データアクセスの規約は `docs/data-access.md`・`docs/architecture.md`、
> リソース追加は `add-supabase-resource` skill、ルート追加は `add-route` skill に従う。

## 8. 検討事項（要決定）

コンセプトを実装に落とす前に決めたい点。

1. **年次サマリーの地図**：常設ページは作らない（→ Phase 2）。Phase 4 の 1 カットとして作る。
   着手前に実データで 3 つを確かめる — ①場所が入っている記録の割合、②ユニークな場所の数、
   ③座標を持てる場所の割合（「通販」「もらいもの」「自宅」はピンにならない。
   **地図は原理的に、常に部分的な表現にしかならない**）。
   作ると決めたらプロバイダ選定（MapLibre／Mapbox／Google Maps）を、コストと
   「落ち着いたダークな地図にできるか」で行い、店名・住所からのジオコーディング手段も併せて決める。
2. **カテゴリ設計**：固定カテゴリか、カテゴリごとの可変メタ項目をどこまで作り込むか（Phase 1 の粒度）。
3. ~~**評価軸**~~：**決着済み**。0〜10 のスライダー（0.1 刻み）を「その夜の一杯の印象」として残す。
   TOP10 は評価から計算しないので、評価軸の精度が順位に効くことはない（→ Phase 3）。
4. **写真**：画像アップロードを Phase 1 に含めるか（Supabase Storage 利用）。
5. **限定共有の方式**：公開リンク（推測不能な URL）方式か、閲覧側もログイン必須か。
6. **サマリーの共有ビジュアル**：画像書き出し（OGP/シェア画像）まで作るか。

---

## 9. 非目標（やらないこと）

- 飲む量・回数を煽る／過度なゲーミフィケーション。
- フルオープンな SNS（フォロー・タイムライン・拡散）。
- 常時ふざけた UI。遊び心は「要所」限定。
